Integration design · Matrix COSEC → ZingHR · rev 4

Punch to Payroll

One day's swipes per night, each sent exactly once. Recovery comes from a ledger that remembers what succeeded rather than from re-sending — which costs a little state and buys back everything the trailing window was doing for free.

COSEC · GET · Basic auth → Ledger · day + swipe state → ZingHR · JWT (2 min) · POST

1 · The trade

An earlier revision bought crash-recovery, missed-run recovery and late-arrival coverage from a single mechanism: re-send a trailing window every night and let ZingHR absorb the duplicates. Dropping that is the right call — it was paying for our convenience with sevenfold write amplification in someone else's payroll tables, indefinitely — but it was doing real work, and that work has to move somewhere.

The design in one line

State is the price of not re-sending. To send each swipe exactly once, the system has to remember which ones it has already sent — so a durable ledger stops being optional. What that buys back is precision: recovery re-sends only what genuinely failed, instead of a week of data that mostly succeeded.

On a normal night, exactly one day's swipes are sent, each exactly once. Nothing is re-sent unless it demonstrably did not land.

Two levels of granularity make that work. A day job tracks whether an attendance date has been fully delivered, so a night the server was down is picked up tomorrow rather than lost. A per-swipe record tracks individual delivery, so a retry re-sends the three rejected rows rather than the four thousand that were fine. The second level is what keeps duplicates near zero — retry at day granularity would re-send an entire day to fix one record.

2 · Re-read is not re-send

Dropping the trailing window removes the only mechanism that caught late-arriving swipes — a terminal that loses its network link, buffers locally, and uploads days later. Those swipes carry an old swipeDateTime, so a job that fetches only yesterday will never see them, and nothing will error, because you never learn they exist.

The resolution is that these are two different operations, and only one of them was ever the problem:

OperationCostDo it
Re-read a day from COSECA LAN request to a server on the same premises. A few MB. Nobody's data is touched.freely
Re-send a day to ZingHRRows accumulating permanently in a third party's payroll database.never, unless it failed

So keep the sweep and drop the amplification. Each night, after handling yesterday, re-fetch the previous several days from COSEC and insert into the ledger with insert-or-ignore on (terminal_id, unique_id). Rows already there collapse to a no-op. Anything genuinely new — the back-filled buffer from an offline terminal — lands as pending and goes out on the same run.

On a typical night this sweep inserts nothing and sends nothing. When a terminal has been down, it sends exactly the swipes that were missing and not one more. That is strictly better than both alternatives: full late-arrival coverage, zero duplicate sends.

This is what the ledger is for

Note that the sweep is only possible because there is local state. Without a record of what has been seen, the only way to be sure a late swipe gets delivered is to re-send the window blindly. The ledger is what lets aggressive re-reading coexist with minimal writing — the two requirements that looked contradictory.

3 · The ledger

SQLite in WAL mode, single file on the same box. Two tables carry the design; the third is audit.

  unique_id         TEXT

  swipe_datetime    TEXT       -- the other; passed through verbatim

  state             TEXT       -- pending|in_flight|sent|quarantined|abandoned
  attempts          INTEGER    -- record-scoped failures ONLY (see §6)
  ambiguous_count   INTEGER    -- sends that ended in an unknown outcome (§7)
  next_attempt_at   INTEGER
  last_error        TEXT
  created_at, sent_at
  UNIQUE (terminal_id, unique_id)      -- makes re-reading idempotent
  INDEX (state, next_attempt_at)
  INDEX (attendance_date, state)

run_log
  id, started_at, finished_at, outcome,
  days_processed, fetched, sent, rejected, ambiguous, correlation_id

Three notes on the shape:

  • The unique constraint is what makes §2 safe. Re-reading a day repeatedly is a no-op at the database level, with no application logic to get wrong. Scope it on (terminal_id, unique_id) rather than unique_id alone — "1212" looks like a per-device sequence, and keying on it alone would silently discard real swipes from other terminals as duplicates.
  • No lease columns. An earlier revision needed lease TTLs because publishers could run concurrently. Here runs are nightly and a lock file guarantees one at a time, so crash recovery is simply reset every in_flight row to pending at run start. One statement instead of a lease protocol.
  • Keep cosec_count. It is what lets the daily report assert that what COSEC held for a date matches what was delivered, rather than assuming it.

4 · The nightly run

nightly at 00:30, under a lock file:

  0  reclaim:  UPDATE swipe_event SET state='pending'
               WHERE state='in_flight'          // crash recovery

  1  ensureDay(yesterday)                        // create job if absent

  2  days = sync_day WHERE state != 'complete'
         ORDER BY attendance_date ASC            // oldest first
     for each day:
       if state == 'pending':
            rows = cosec.fetch(day)              // retry per §6
            insertOrIgnore(rows)                 // dedupe on (terminal, uid)
            day.cosec_count = rows.length
            day.state = 'staged'

  3  sweep: for d in [yesterday-1 .. yesterday-SWEEP_DAYS]:
            rows = cosec.fetch(d)                // cheap, LAN
            insertOrIgnore(rows)                 // normally inserts nothing

  4  publish: batches of pending/retry-eligible swipes, oldest day first
       for each batch, strictly serially:
            token = zinghr.authenticate()        // fresh; 2-min TTL
            res   = zinghr.post(batch, token)
            assertBodySaysSuccess(res)           // never trust 200 alone
            markOutcomes(batch, res)             // per record

  5  settle: day.state = 'complete' when no swipe for that date
             is still pending or in_flight
             day.state = 'stalled' if incomplete for STALL_DAYS

  6  write run_log · ping heartbeat · email report

Step 2 is where missed-run recovery lives. Because incomplete days stay in the table and are selected oldest-first, a night the server was down is simply processed the following night alongside the new day — without re-sending anything that already succeeded.

Bound the catch-up

If the job has been dead for three weeks, step 2 will try to process twenty-one days in one run, which can blow past the run window and hammer both APIs. Cap days-per-run at a configurable limit — oldest first, so it drains steadily over successive nights — and alert as soon as the backlog exists rather than when it clears.

5 · State machines

The quarantined → pending edge is worth calling out, because it handles the most common rejection without any intervention. A new joiner is enrolled on the biometric device before HR creates their master record, so their swipes are rejected as an unknown employee. Retrying nightly means those swipes deliver themselves the day HR fixes the master — no dead-letter queue, no replay tooling, no ticket.

6 · Retry policy

Retries operate at whichever scope the failure actually belongs to. Getting this wrong is what turns one bad afternoon into a queue full of good records marked failed.

FailureScopePolicy
COSEC unreachable or timing outday3 attempts, jittered backoff. Then leave the day pending — tomorrow's run retries it. Nothing is lost and nothing needs a human.
COSEC returns malformed or truncated datadayDo not stage a partial day. If the row count hits a suspiciously round number, treat it as capped and page or narrow the range. Staging a truncated day then marking it complete is the one way this design still loses data silently.
ZingHR auth failsrun3 attempts, then abort the run — every batch needs a token, so there is nothing useful to continue with. Days stay incomplete and retry tomorrow. Alert, since a rotated secret or expired client credential needs a human either way.
Connect-phase failure — DNS, TLS, connection refusedbatchSafe to retry freely. The request never reached ZingHR, so there is no duplicate risk. Distinguishing this from the case below is worth the plumbing — see §7.
5xx with a response bodybatchServer answered and declined. 3 attempts with full jitter — random(0, min(cap, base·2ⁿ)) — then leave the records pending for tomorrow. No duplicate risk; the response tells you it was not processed.
Response-phase failure — timeout or reset after the request was sentbatchAmbiguous. Outcome genuinely unknown. Handled separately in §7, not by this ladder.
POST returns 401batchRe-authenticate and retry once. If a fresh token is also rejected, stop — credentials or client config are wrong and retrying will not fix it.
POST returns 429batchHonour Retry-After, then backoff. Unlikely at one run a night, but free to handle.
Record rejected — unknown employeerecordQuarantine, retry once per night for QUARANTINE_DAYS (7 is reasonable), then abandon and report. Covers the new-joiner case automatically.
Record rejected — malformed or business-invalidrecordNo retry; the same payload will be rejected identically. Quarantine and report immediately so it can be looked at while the context is fresh.
Whole batch rejected, offender unidentifiedbatchBisect — split and retry halves, recursing only into failing ones. Eight requests to isolate one bad record in 200. Only on permanent-classified failures, never transient.
Process crash mid-runrecordNext run resets in_flight to pending. Note this is itself an ambiguous case — the batch may have landed before the crash — so count it per §7.

Only count attempts against the record when it is the record's fault

The distinction that matters most here. A ZingHR outage is not a property of the payload — if a five-hour outage increments attempts on every record in every retried batch, an entire day of perfectly good swipes marches into abandoned and gets dropped from payroll, with the logs showing "max attempts exceeded" as though the data were bad.

So: batch- and run-scoped failures leave attempts untouched and return records to pending. Only a rejection naming that specific record increments it. The day-level stalled state is what escalates a sustained outage to a human, not the record counter.

7 · The ambiguous timeout

The design sends each swipe once. There is exactly one case it cannot eliminate: a POST is sent, the connection drops or times out before a response arrives, and there is no way to know whether ZingHR processed it. Retrying risks a duplicate; not retrying risks a permanent hole. No protocol between two parties can resolve this, so it is a choice about which error to prefer.

Yes, they are retried — but on a different ladder

An ambiguous batch goes back to pending and is retried, because a duplicate swipe is tolerated by ZingHR's pairing logic while a missing swipe is an employee short on hours. Prefer the harmless error. But it must not ride the ordinary retry ladder, for a reason that is easy to miss:

Each retry can itself end ambiguously

If ZingHR is degraded rather than down, an ambiguous timeout is likely to be followed by another. Run three backoff attempts and each may have landed — you can produce four copies of the same swipe while believing you sent none. The ordinary ladder assumes a failed attempt did nothing, which is precisely what is not known here, so applying it multiplies the harm it is meant to contain.

So the policy is deliberately timid:

  • One immediate retry, then stop for the night. If that also ends ambiguously, return the records to pending and let tomorrow's run handle them. A day sitting incomplete for 24 hours costs nothing; four copies in payroll costs a conversation.
  • Increment ambiguous_count, not attempts. The record is not at fault, so it must not march toward abandoned (§6). But the count needs to exist, because it is the only visibility into how many possible duplicates have been created.
  • Shrink the batch on the retry. Retrying a 200-record batch risks 200 duplicates; splitting it first bounds the blast radius, and a smaller request is likelier to complete against a struggling server.
  • Report every one, and alert on clusters. A handful a year is the cost of doing business over a network. A dozen in a week is a network or capacity problem worth finding, and the log is what makes it findable.

Most "timeouts" are not actually ambiguous

Worth the plumbing, because it shrinks this whole category: a failure before the request was sent carries no duplicate risk at all. DNS failure, connection refused, TLS handshake failure — ZingHR never saw it, so retry freely on the normal ladder. Only a failure while awaiting a response is genuinely unknown.

Set separate connect and response timeouts rather than one overall deadline, so the two are distinguishable at the point of failure. Undici exposes connectTimeout, headersTimeout and bodyTimeout separately for exactly this. With a single combined timeout you cannot tell which happened and must pessimistically treat everything as ambiguous — which is how a design ends up creating duplicates it never needed to.

The ambiguity can sometimes be resolved rather than guessed

If ZingHR exposes any endpoint to read back swipes for an employee and date, the guess disappears: query before retrying, and the outcome becomes known. Their API surface has not been explored beyond auth and sync, so this is worth asking about — it converts the one unavoidable defect in this design into a solved problem, and it is cheap to use at the volume involved (only after an ambiguous failure, which should be rare).

Everything else is genuinely once-only: crash recovery re-sends only records never acknowledged, day retries re-send only what is still pending, and the §2 sweep sends only rows that were not already in the ledger. This is what "occasional duplicates" was always meant to describe — a rare unavoidable race, bounded and counted, not a scheduled weekly re-send.

8 · Failure handling

Beyond the retry table, four things still need handling — none of them affected by the single-day scope change.

  • 200 OK with a failure body. Still the most dangerous case and the least visible. HRMS APIs routinely return 200 for business rejections, so parse the body and derive outcome from it — a run reporting success while payroll received nothing is what you would discover at cutoff. This matters more without a trailing window, not less: a false "sent" here means the record is marked delivered in the ledger and never retried, where a nightly re-send would have papered over it. Capture the real error shape on UAT by sending a deliberately bad record.
  • An external dead-man's switch. A nightly job can be dead for a fortnight before anyone notices. Ping a heartbeat URL on success and let an outside watcher alert when the ping stops — internal monitoring cannot detect its own absence.
  • Explicit timeouts on every call. Node has no default request timeout, so an unset one hangs forever, and a job hung since 00:30 is indistinguishable from one that never ran. Set them per-phase, per §7.
  • The client secret's configurable expiry. Whatever it is set to, it is a date on which this stops working with an auth error and no other warning. Set it as long as policy permits, record the date where a human will see it, and name it as a likely cause in the auth-failure alert.

The daily report

One email per run, sent whether or not anything went wrong — at one run a day, silence is exactly what a dead job looks like. Per day processed: COSEC count, sent, quarantined. Plus any stalled days, the quarantine list with ages, abandoned records, ambiguous sends with their running counts, and run duration.

The alerts worth interrupting someone for are narrow: no successful run in over 24 hours, a day stalled beyond its threshold, auth failure on either side, any record abandoned — the only path by which a swipe is permanently not delivered — and a cluster of ambiguous sends, which is the early warning for a network problem that will otherwise show up as mysterious duplicates.

9 · Code shape & config

TypeScript, undici for per-phase timeouts, zod at both boundaries, better-sqlite3 for the ledger (synchronous and transactional, no pool to reason about), pino with credential redaction from the first commit. Still no queue and no broker.

Publishing stays strictly serial: the JWT lives two minutes and issuing a new one invalidates the previous, so two concurrent batches would void each other's tokens and produce 401s that depend on timing. Authenticate immediately before each POST and use the token once — at a two-minute TTL, cache-and-refresh logic compares their exp against your clock, where a minute of drift is half the budget.

10 · Build order

  1. Phase 1 · days 1–3Ledger and happy path

    Migrations, both state machines, and one day flowing end to end with no retry logic. Prove the two-field mapping and the round trip against UAT.

  2. Phase 2 · days 4–6Retry layer

    Error classification including the connect-vs-response split, the scope rules from §6, backoff, quarantine with nightly re-drive, bisection. The scope distinction — batch failures must not increment record counters — deserves a test of its own, since getting it wrong is invisible until an outage.

  3. Phase 3 · week 2Sweep and recovery

    The §2 re-read sweep, crash reclaim, bounded catch-up. Test by unplugging a terminal, swiping on it, reconnecting after the day is marked complete, and confirming the swipe reaches ZingHR without anything else being re-sent.

  4. Phase 4 · week 2–3Operability

    Daily report, alerts, heartbeat, CLI. Not polish — it is what makes this supportable by someone who is not you.

  5. Phase 5 · week 3Shadow run

    Production COSEC with DRY_RUN=true for a full pay cycle. Employee-mapping churn and volume surprises appear here rather than in a payroll run.

  2. What do rejections actually look like — status codes and body shape?Your Q13. The whole retry policy classifies on this, so send a bad employee code and a malformed record deliberately and record exactly what comes back.
  3.
